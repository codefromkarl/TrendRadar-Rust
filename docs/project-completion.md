# 项目完结说明

## 文档目标

这份文档用于给当前仓库一个正式的完结口径。

这里的“完结”不是指：

- 原版 Python 的全部能力都已迁到 Rust
- 仓库以后完全不再变化
- 不再允许任何 bugfix 或文档修正

这里的“完结”指的是：

- 这次以 Rust 迁移与 vibecoding 练手为目标的项目阶段已经完成
- 当前仓库已经形成一个可运行、可验证、可复查的 Rust 趋势监控内核
- 后续不再默认继续扩需求，而是转入维护模式

## 本次项目的完成定义

到当前节点，以下目标已经达成：

1. 迁移前基线已固定为 Python 原版 `v6.6.1`
2. Rust 版主链路已经闭环：`config -> fetch -> analyze -> storage -> report -> CLI`
3. 已具备真实 HTTP 抓取、结构化输出、本地存储和运行日志能力
4. 已形成系统性测试、文档基线和验证门禁
5. 已完成一次以 AI 协作主导的 Rust 项目实践闭环

## 当前已完成范围

当前可以视为已完成的范围包括：

- 配置模型、默认值、校验与文件加载
- RSS / 热榜抓取路径
- 排序、来源聚合、领域摘要
- 高热度保底、来源保底、领域保底
- 跨来源标题去重
- SQLite 本地存储
- JSON / HTML / Table / Markdown 输出
- 结构化运行日志
- 通知最小可扩展模型
- 最小 AI 分析旁路
- 最小 MCP 查询型工具服务
- Rust / Python 基线对比文档
- 项目口径、迁移对比、vibecoding 复盘文档

## 当前不再默认继续做的事情

从这份文档提交开始，下面这些工作不再作为默认继续开发目标：

- 继续追平 Python 原版剩余全部能力
- 继续扩大通知渠道矩阵
- 继续补完整 MCP 协议层
- 继续补完整 AI provider / 翻译矩阵
- 继续把项目往“更完整产品”方向无限扩张
- 因为“还能做更多”而继续追加需求

## 后续模式

当前仓库从现在开始按**维护模式**理解。

默认只接受下面几类变更：

- 明确 bugfix
- 依赖或工具链兼容性修复
- 文档错误修正
- 小范围可验证优化

不再默认接受：

- 开放式功能扩张
- 模糊目标的新一轮重构
- 没有完成边界的新主题并入主线

## 完结后的维护与占用口径

项目完结后，仓库默认按“源码、文档、fixtures 和 Git 历史是项目本体；`target/`、本地索引缓存和临时运行产物是可重建本地状态”来理解。

日常开发仍优先保留增量编译缓存，使用 `cargo sweep --time 7` 或 `just sweep` 清理旧缓存。只有在项目封存、交接、磁盘回收或明确不再继续本地开发时，才建议使用 `cargo clean` 做全量清理。

这一区分很重要：

- 维护开发中，过度清理 `target/` 会拉长下一次 `cargo check` / `cargo test` 的反馈时间。
- 项目阶段结束后，清理 `target/` 和失败的本地索引目录不会改变仓库可复现性。
- 仓库文档不应把本机临时绝对路径、缓存目录或一次性索引状态写成项目事实。

完结后的具体整理记录见 [开发记录：AI 原生开发收口与本地占用整理](./dev-journal/2026-04-27-ai-native-closeout-and-disk-cleanup.md)。

## 对这次项目的最终判断

如果把这次项目定义为：

> “验证是否可以主要依靠 vibecoding 完成一个 Rust 迁移项目，并把它收口成可运行、可验证的成果”

那么这个目标已经完成。

它已经不需要继续通过新增功能来证明自己成立。

## 完结后的建议动作

1. 保持主分支干净。
2. 后续如有新想法，优先开独立主题而不是继续堆在主线。
3. 任何新增需求先问一句：
   这是维护，还是重新开一个新阶段？
4. 如果答案是“新阶段”，先写新边界，再开始开发。

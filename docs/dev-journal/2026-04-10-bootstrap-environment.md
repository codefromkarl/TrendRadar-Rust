# 开发记录：基础环境准备

## 基本信息

- 日期：2026-04-10
- 阶段：项目初始化
- 主题：Rust 基础环境、工程骨架与质量门禁准备
- 目标：把仓库初始化成一个可开发、可验证、可持续扩展的 Rust 工作区

## 背景

Rust 项目如果一开始没有把工具链、格式化、lint、测试和 CI 统一好，后面随着 crate 数量增加，开发效率会迅速下降，AI 参与开发时也更容易出现风格漂移、结构失控和验证不一致的问题。

因此这一阶段优先处理的不是业务功能，而是“工程基础设施”。

## 本次完成内容

- 建立了 Rust workspace 和基础 crate 骨架
- 固定了 toolchain、格式化和 lint 配置
- 增加了 `justfile` 作为统一命令入口
- 增加了 GitHub Actions CI 骨架
- 补充了最小 smoke test，验证工作区可以通过编译和测试
- 增加了迁移文档和架构文档
- 补充了独立的环境准备文档
- 在 `README.md` 中明确了 License 和迁移来源说明
- 补充了 AI 协作准备说明，包括 skills、上下文管理和代码索引策略

## 关键决策

### 决策 1

- 决策内容：先搭工程基础设施，再开始业务迁移
- 原因：没有统一的验证闭环，后续任何模块迁移都会不断返工
- 备选方案：先实现一个核心模块，再补工具链
- 为什么没有选备选方案：这样会把结构、风格和测试策略都做成临时方案，后面要重新收口

### 决策 2

- 决策内容：采用 workspace + 多 crate 骨架，而不是单 crate 起步
- 原因：项目目标本身就是内核化和模块化迁移，早一点划清边界成本更低
- 备选方案：先用单 crate，后续再拆
- 为什么没有选备选方案：单 crate 前期快，但后续拆分时容易把耦合固化

### 决策 3

- 决策内容：初始化阶段只保留稳定、必要的 lint 规则
- 原因：过严的规则会让初始化阶段被元数据和风格噪音拖慢
- 备选方案：一开始就全面打开 `clippy` 高强度规则
- 为什么没有选备选方案：收益不高，而且会把注意力从系统边界转移到细枝末节

### 决策 4

- 决策内容：在 README 中明确写出该仓库从 TrendRadar 迁移而来，并先按 GPL-3.0-only 处理 License
- 原因：迁移项目如果不在最开始就讲清来源和许可边界，后续容易出现文档、协作和治理上的歧义
- 备选方案：先只写技术信息，后续再补许可证和来源说明
- 为什么没有选备选方案：这会把最重要的项目信息延后，增加后续返工和误解风险

### 决策 5

- 决策内容：在环境准备阶段就把 AI 协作方式文档化，而不是只保留在实际操作里
- 原因：这个项目本身就是 AI 辅助迁移，如果不把 skills、上下文管理和索引策略写清楚，后续协作会依赖个人记忆
- 备选方案：先默认沿用当前 AI 使用方式，等以后再补文档
- 为什么没有选备选方案：AI 协作本身已经是工程流程的一部分，应该和工具链、CI、测试一起纳入初始化范围

## 遇到的问题

### 问题 1

- 现象：首次运行测试时，workspace 成员缺失导致 manifest 加载失败
- 原因判断：只创建了根配置和单个 crate，尚未补齐全部工作区成员
- 处理方式：统一补全所有 crate 的 `Cargo.toml` 与 `src/lib.rs`
- 最终结果：工作区成功完成编译和测试

### 问题 2

- 现象：`clippy` 因 lint group 优先级和 cargo 元数据缺失报错
- 原因判断：初始化时把 lint 配置设得过满，且 package 元数据没有一次补齐
- 处理方式：下调 lint group 优先级，统一补全 workspace 级描述字段
- 最终结果：`cargo clippy --workspace --all-targets --all-features -- -D warnings` 通过

### 问题 3

- 现象：`rustfmt.toml` 中部分配置在 stable 工具链下产生警告
- 原因判断：使用了仅 nightly 支持的格式化选项
- 处理方式：移除 unstable 配置，只保留稳定配置项
- 最终结果：`cargo fmt --all --check` 无警告通过

### 问题 4

- 现象：本地未安装 `cargo-nextest` 和 `cargo-deny`
- 原因判断：仓库初始化时只建立了工具入口，还没有完成机器级工具安装
- 处理方式：增加 `scripts/bootstrap.sh` 和 `README` 说明，后续统一安装
- 最终结果：基础 `cargo test` 可运行，高阶工具等待环境安装

### 问题 5

- 现象：初始化阶段虽然有基础 README，但没有明确写清项目迁移来源和 License 边界
- 原因判断：前一阶段重点放在工程骨架和验证闭环，项目身份信息补充得不够完整
- 处理方式：补充环境准备文档，并在 `README.md` 中增加迁移来源与 `GPL-3.0-only` 说明
- 最终结果：仓库对外信息更完整，后续协作边界更清楚

### 问题 6

- 现象：虽然项目已经在使用 AI 搜索、上下文管理和验证流程，但这些做法没有被显式记录
- 原因判断：最初注意力主要集中在 Rust 工具链和 workspace 初始化，对 AI 协作层的沉淀不够
- 处理方式：在环境准备文档中新增 AI 协作准备章节，明确 skills、ContextAtlas 和代码索引顺序
- 最终结果：AI 协作方式正式进入项目文档，后续迁移流程更容易复用

## 经验与心得

### 做对的地方

- 先把仓库变成“可验证系统”，而不是急着写业务逻辑
- 在初始化阶段就建立文档、CI 和命令统一入口，后面会省很多沟通成本
- 在正式进入业务开发前，先把迁移来源和 License 说明写清楚
- 把 AI 协作方式也纳入初始化文档，而不是默认它只是隐性工作流

### 可以改进的地方

- 可以更早预判 `clippy::cargo` 对元数据的要求，减少一次返工
- 可以更早确认 stable / nightly 配置边界，避免 `rustfmt` 警告

### 对后续开发的提醒

- 后续每新增一个 crate，都应继承当前 workspace 约束，不要自己单独立规则
- 业务迁移前最好先补一批 fixture 和回归测试样例
- 不要在没有测试样本的情况下直接迁复杂模块

## AI 原生开发注意要点

这次项目最有价值的结论不是“AI 可以写很多代码”，而是“AI 必须在明确控制面里写代码”。

后续如果继续做类似项目，建议固定下面这些规则：

- 先定义阶段、非目标和完成标准，再让 AI 做实现。
- 让代码、测试、文档和 Git diff 成为最终事实来源，不让会话记忆替代仓库证据。
- 每轮任务只保留一个主目标，避免 AI 把“顺手补齐”扩成半个新里程碑。
- 文档要记录边界、取舍和停止规则，不要只记录功能清单。
- 实现、审查和验证尽量分离；执行者不能作为自己工作的最终验证者。
- 完结后要切到维护模式，只接受明确 bugfix、小范围优化和有新边界的新阶段。

## 本地占用整理结果

本轮整理前，仓库占用主要来自 Rust 构建产物：

- `target/`：约 `5.4G`
- 仓库源码、文档、fixtures 和 Git 元数据：不到 `10M`

本轮执行了两类清理：

- `cargo sweep --all`：清理旧构建缓存，释放约 `4.56GiB`
- `cargo clean`：在项目已进入维护模式后，清理剩余当前构建产物，释放约 `1.1GiB`

清理后，仓库本地占用约 `9.0M`。

如果清理后继续运行 `just verify-basic`、`cargo check` 或 `cargo test`，`target/` 会被重新生成。这不改变本轮清理结论，只说明 Rust workspace 的构建缓存属于可重建本地状态。

## 维护模式下的清理口径

日常开发时，不建议把 `cargo clean` 放进常规验证流程，因为它会破坏增量编译缓存，显著拖慢下一次 `cargo check` / `cargo test`。

维护收口、项目封存、交接或磁盘回收时，可以使用 `cargo clean`，因为这些场景的目标是降低本地占用，而不是优化下一轮开发反馈速度。

推荐口径：

- 日常开发：优先 `cargo sweep --time 7` 或 `just sweep`
- 阶段收口：可以 `cargo sweep --all`
- 项目封存或磁盘回收：可以 `cargo clean`

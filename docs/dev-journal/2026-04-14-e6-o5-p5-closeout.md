# 开发记录：E6 / O5 / P5 收口

## 基本信息

- 日期：2026-04-14
- 阶段：迁移收尾
- 主题：E6、O5 与 P5 的最小闭环收口
- 目标：把当前 Rust 内核重构迁移从“接近收口”推进到“可以进入收尾阶段”

## 背景

在前一阶段结束时，仓库已经具备稳定的主链路和较完整的验证闭环，但还有三块内容没有真正收掉：

- `E6` 只有 Rust 内部 benchmark 基线，没有真实 Python 对比值
- `O5` 已有多条高价值测试，但还缺“多轮复杂场景稳定不抖动”的最后一道收口
- `P5` 在路线图里仍是待办，通知层虽然已有多渠道实现，但还没有进入可扩展 sink 模型

如果这三块继续悬而未决，仓库会长期停留在“几乎完成，但还不能干净收尾”的状态。

## 本次完成内容

- 同步更新 `docs/roadmap.md`、`docs/contracts/config.md`、`docs/implementation/app.md`、`docs/migration-guide.md` 和 `docs/acceptance-matrix.md`

## 关键决策

### 决策 1

- 决策内容：Python benchmark 不直接改旁边 Python 仓库，而是在 Rust 仓库内增加 bridge 脚本
- 原因：当前 Python CLI 没有暴露可配置的 hotlist API base URL，无法仅靠配置完成离线 fixture 对齐
- 备选方案：直接修改旁边 Python 仓库，加 benchmark 入口或额外参数
- 为什么没有选备选方案：会突破当前仓库边界，也会把本轮收口从“收尾”扩成“跨仓协同改造”

### 决策 2

- 决策内容：O5 只补一条“复杂场景多轮稳定性”测试，不继续横向扩更多组合
- 原因：当前主链路已经稳定，O5 的价值在于证明不抖动，而不是继续堆测试数量
- 备选方案：继续扩更大输入、更多失败源、更多 parser 组合
- 为什么没有选备选方案：收益已经开始递减，会拖慢收尾节奏

### 决策 3

- 决策内容：P5 先做“可扩展 sink 模型 + Slack sink + 兼容旧字段”，不一次性扩 Telegram / Discord
- 原因：要先把通知层的扩展边界建立起来，再决定后续具体渠道
- 备选方案：继续沿用平铺 webhook 字段，直接再加 1 到 2 个新渠道
- 为什么没有选备选方案：只加渠道不改边界，会把通知层继续锁死在硬编码结构上

## 遇到的问题

### 问题 1

- 现象：Python 真实 CLI 虽然已确认是 `python -m trendradar`，但热榜 API 地址在实现里写死，不能直接通过配置切到本地 fixture
- 原因判断：Python 仓库当前仍沿用固定 API 基址，而不是配置驱动
- 处理方式：bridge 脚本里复用 `NewsAnalyzer.run()`，同时 monkeypatch `DataFetcher.DEFAULT_API_URL` 并通过本地 HTTP server 提供 fixture
- 最终结果：不改 Python 仓库代码，也能完成真实主流程测量

### 问题 2

- 现象：通知层已有多个渠道实现，但 app 侧仍按平铺字段直接调用 `build_notifiers()`
- 原因判断：此前的多渠道扩展是按“补功能”推进的，还没有回到配置建模层统一收口
- 处理方式：在 `config -> app -> notification` 三层同时补 `sinks`、spec builder 和兼容合并逻辑
- 最终结果：通知层已具备最小可扩展模型，同时不破坏旧配置

## 经验与心得

### 做对的地方

- 把 E6、O5、P5 当成一组“收口包”处理，而不是继续拆成零散小尾项
- O5 只补最后一条高价值测试，没有重新打开大规模测试扩张
- P5 先做边界，再做渠道，避免“多加一个 webhook 渠道”式的局部优化

### 可以改进的地方

- 更早识别 Python CLI 的 hotlist API 配置限制，可以少走一次“直接复用 CLI”的验证路径
- 文档里的通知配置口径此前更新略慢，说明契约文档在扩展阶段仍然需要更及时同步

### 对后续开发的提醒

- 当前“迁移收尾”已经足够结束，不要再以收尾名义继续扩 E6/O5/P5
- 后续若继续做通知渠道，应按 `notification.sinks` 增量推进，而不是回退到旧平铺字段模型
- 之后的新任务更适合定义成“增量演进”或“生态扩展”，而不是继续挂在“迁移尚未完成”

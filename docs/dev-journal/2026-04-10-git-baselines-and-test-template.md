# 开发记录：Git 初始化、迁移基线与系统测试模板

## 基本信息

- 日期：2026-04-10
- 阶段：项目初始化后续收敛
- 主题：建立 Git 工作树、迁移基线文档和系统性测试模板
- 目标：把仓库从“可编译骨架”推进到“可审查、可切分、可验证”的迁移工地

## 背景

虽然当前仓库已经具备 workspace、lint、CI 和基础 smoke test，但对于真正的 Rust 迁移来说，这还不够。

如果没有 Git 工作树、迁移基线和系统性测试模板，AI 在多轮迁移中仍然容易出现：

- 任务切分不稳定
- 契约边界模糊
- fixture 和测试挂载点缺失
- 文档和实现逐步偏离

因此这一轮补的不是新功能，而是迁移过程本身的底座。

## 关键决策

### 决策 1

- 决策内容：先把 Git 工作树建立起来，再补充迁移模板
- 原因：没有 Git，很多工程流程只能停留在口头约束
- 备选方案：先只写文档，后续再处理版本控制
- 为什么没有选备选方案：文档同步脚本、分支隔离和 diff 审查都依赖 Git 工作树

### 决策 2

- 决策内容：先写“基线文档 + 模板”，不伪造一份已经完成的旧系统契约清单
- 原因：当前仓库还在迁移前期，先把结构搭对，比提前填满内容更重要
- 备选方案：现在就写完整旧系统接口表
- 为什么没有选备选方案：那样容易写出未经验证的伪事实

### 决策 3

- 决策内容：系统性测试先定义模板和目录，再按 crate 逐步补真实样例
- 原因：当前代码实现还很薄，直接铺大量测试文件会制造空壳噪音
- 备选方案：先创建一批占位测试源码
- 为什么没有选备选方案：无输入样例、无真实链路的占位测试意义不大

## 经验与心得

### 做对的地方

- 把“AI 可读、可执行、可验证”进一步落成仓库文件，而不是只靠口头约定
- 把系统性测试、fixture 和迁移基线放到现有目录结构中，减少后续重排

### 还需要继续补的地方

- 旧系统到 Rust crate 的细粒度模块映射仍需按真实迁移进度补全
- 真实 fixture 和 parity 样例还没有进入仓库
- 契约文档还需要随着 `config`、`fetch`、`report` 的真实实现逐步固化

# Vibecoding 复盘：如果全程用 AI 协作实现 Rust 项目，需要注意什么

## 目标

这份文档不是讲“AI 好不好用”，而是复盘：

- 如果把这个 Rust 迁移项目当成一次全程 vibecoding 实验
- 哪些地方真的有效
- 哪些地方最容易失控
- 开始之前应该准备什么
- 中途如何防止项目被 AI 带偏

## 先说结论

**Rust 项目可以大量使用 vibecoding，但不能把“AI 连续产出代码”误当成“项目自然会收敛”。**

在 Rust 里，编译器能帮你挡住很多低级错误，但挡不住下面这些更贵的问题：

- 项目边界失控
- 文档口径漂移
- 配置语义越来越乱
- 测试没有覆盖真正业务风险
- 代码虽然能编译，但产品越来越不像你最初要的东西

所以，如果真要全程 vibecoding，最重要的不是“让 AI 一直写”，而是**先设计好约束系统**。

## 这次项目里，vibecoding 最有效的部分

### 1. 文档先行

最有效的不是直接写代码，而是先把这些东西写出来：

- 迁移边界
- 模块职责
- 完成标准
- 验证命令
- 任务切分方式

一旦这些内容先落成仓库文件，AI 的输出就明显更稳。

### 2. 固定验证入口

Rust 项目特别适合把 vibecoding 放在一套固定门禁下运行：

- `cargo fmt --all --check`
- `cargo test`
- `just verify-basic`
- `git diff --check`

只要没有这一层，AI 会不断产出“看起来合理、实际上未验证”的代码和文档。

### 3. 把任务切成小闭环

最顺的节奏不是“大功能一把写完”，而是：

- 一个配置字段
- 一条测试链路
- 一个 fetcher
- 一个输出模式
- 一个保底策略
- 一份运行日志

Rust 很吃边界清楚；AI 也一样。
任务越小，AI 越不容易把上下文搅乱。

### 4. 让 AI 负责实现，让验证负责裁决

真正可靠的工作流不是“AI 说完成了”，而是：

- AI 负责改代码
- 测试负责判断行为
- 文档负责收口口径
- Git diff 负责最后审查

## 全程 vibecoding 最容易出问题的地方

### 1. 口径漂移

这是这类项目最常见的问题。

表现是：

- README 一套说法
- 路线图一套说法
- 代码已经变了
- 日志还在写旧状态

AI 非常容易在不同回合里沿着旧上下文继续写，从而把过期口径越写越多。

### 2. 看起来在实现，实际上在扩 scope

Rust 项目里很容易发生这种情况：

- 原本只是补一个字段
- 后来顺手补通知
- 再顺手补日志
- 再顺手补多领域
- 最后 scope 已经不是原任务了

AI 很擅长“顺带优化”，但这恰恰是项目失控的开始。

### 3. 编译通过，不等于产品方向正确

Rust 的一个陷阱是：

- 代码能编译
- 测试也可能通过
- 但产品已经悄悄偏了

例如：

- 过滤逻辑改得更复杂了
- 输出模型越来越像内部调试结构
- 用户真正关心的信息却还没进入结果面

这类问题编译器不会提醒你。

### 4. AI 会天然倾向“继续做更多”

如果不人为约束，AI 会非常自然地把项目往下面方向推：

- 再补一个格式
- 再补一个字段
- 再补一个来源
- 再补一个 provider

所以对于练手型项目，最重要的能力不是“让 AI 持续产出”，而是**及时叫停**。

## 如果从零开始，全程 vibecoding 前要准备什么

### 1. 一份项目边界文件

至少先写清：

- 这个项目是做什么的
- 不做什么
- 当前阶段目标是什么
- 什么算完成

没有这份文件，AI 会自己脑补目标。

### 2. 一份命令清单

至少明确：

- 允许跑什么命令
- 哪些命令是验证入口
- 哪些命令不能随便跑

这能直接减少大量“临时乱试”的噪声。

### 3. 一份任务切分协议

提前规定：

- 多大任务必须先分析
- 多文件改动先查什么
- 什么时候必须补文档
- 什么时候必须补测试

### 4. 一套最小 fixture

如果没有 fixture，AI 会越来越依赖想象。

一旦有 fixture：

- 抓取能验证
- 排序能验证
- 输出能验证
- 回归能验证

### 5. 一份“停止规则”

练手项目最需要的不是路线图，而是停止规则，例如：

- 主链路闭环后停止扩功能
- 文档和验证一致后进入维护模式
- 后续只接受 bugfix，不再默认扩展功能

## 真想全程 vibecoding，推荐的工作法

### 阶段 1：先写规则，不写功能

先让 AI 帮你写：

- 迁移策略
- 模块映射
- 不变量
- 验收矩阵
- 验证命令

### 阶段 2：让 AI 按最小闭环推进

顺序应该像这样：

- 配置
- 调度
- 数据模型
- 抓取
- 排序/聚合
- 存储
- 输出
- CLI

不要一开始就做“完整产品化”。

### 阶段 3：持续做状态校准

每过一段时间都要做一次：

- README 是否还是最新
- 路线图是否还是最新
- 项目状态是否还准确
- 是否已经超过最初 scope

### 阶段 4：主动收尾

一旦核心目标达成，就要把项目切到：

- 收口
- 维护
- 存档

而不是把 vibecoding 变成无限开发。

## 这次练手项目里，真正要记住的经验

### 做对了的地方

- 先把迁移边界写进仓库，而不是只靠聊天上下文
- 让验证命令成为客观裁决，而不是相信“应该可以”
- 逐步把功能、文档、日志和示例配置一起收口
- 在接近完成时做口径校准，而不是继续盲目扩展

### 以后要更警惕的地方

- 不要把“能继续做”误当成“必须继续做”
- 不要因为 AI 产出快，就把多个需求捆成一次大改动
- 不要等文档和代码已经漂很远了才回头校准
- 不要把编译通过误当成业务完成

## 最终建议

如果目的是“练手验证能不能全程 vibecoding 做 Rust 项目”，这次实验已经足够说明一件事：

**可以，但前提不是放任 AI 一直写，而是你要先把项目变成一个有边界、有门禁、有停止规则的系统。**

没有这些约束，vibecoding 最后练到的不是 Rust，而是“如何把项目越做越散”。
